# Tessera speed map — 6 October 2026

Source baseline: `1d600f426d9439e7440116bb11ce69249451e139`, tree
`b74bb7ee323b4490d22d035553471156f3f601f7`. S0 changes this document only.
No compilation, inference, model fetch or benchmark was performed for S0.
File and line references below describe that baseline, not a future implementation.

The first opportunities are to measure the worker's actual outcome path, avoid
repeating accepted-input tokenization, and avoid bringing a whole token matrix
back to the CPU for CLS pooling. Tensor batching, length sorting and Metal are
separate experiments. Their benefit cannot be inferred from a single-text rate.

## What the source says

### Dense call paths

There are two materially different batch implementations:

| Public entry | Route to forward and return | Work and scheduling |
| --- | --- | --- |
| `encode` | `src/api/embedder/dense.rs:218–233` → `src/encoding/dense/inference.rs:164–171` → `encode_tokenized:425–459` → `forward_tokenized_admitted:364–422` → pooling and output processing | One full text tokenization, one forward, one inference permit. Returns a pooled vector plus an owned copy of the input string. |
| `encode_outcome` | `src/api/embedder/dense.rs:248–263,553–656` → classifier `src/encoding/dense/inference.rs:179–202` → `encode_whole_input:240–246` → the same tensor/forward/pooling route | Accepted text is tokenized for classification, discarded, then tokenized again for inference. Refusals are classified before accepted-item job accounting. The result has counts without retaining the source text. |
| `encode_batch_outcomes` — **worker path** | `src/api/embedder/dense.rs:281–300,553–656` → `src/encoding/dense/inference.rs:205–236,250–272` → one single-input forward per accepted item | Classification is serial; accepted texts are tokenized again, serially. One permit per chunk admits parallel item work using `into_par_iter`; each forward is unpadded. The public comment at `dense.rs:274` says sequential, but the implementation at `inference.rs:231–234` is parallel. |
| `encode_batch` — **tensor batch path** | `src/api/embedder/dense.rs:360–411` → `src/encoding/dense/inference.rs:469–598` → tokenizer `src/core/tokenizer.rs:540–613` | Pads every item to the chunk's longest sequence, forms `[B,L]` tensors, and calls the model once per chunk. A one-item chunk uses `encode`. Jina's unmasked adapter discards the padded tokenization and re-encodes each item separately (`inference.rs:485–491`), preserving its numerical semantics. |
| `encode_windows` / `encode_batch_windows` | `src/api/embedder/dense.rs:56–98,685–799` → planner `src/core/tokenizer.rs:348–456` → `src/encoding/dense/inference.rs:24–59` → single-input forwards | One joined source tokenization plus two special-envelope probe encodes; owned, overlapping token windows; all plans and collected-output budgets checked before forwarding. One permit per group, Rayon work per window, source-ordered vectors and byte spans returned. No tensor padding. |
| `encode_windowed` — aggregate variant | `src/api/embedder/dense.rs:306–328` → `src/encoding/dense/inference.rs:277–315` | Separate API: sequential windows, a permit per window, center-owned weighted mean, final normalization, and an owned source string. This is not native attention over the whole long text (`src/runtime/window.rs:8–11`). |

The model dispatch is `src/encoding/dense.rs:60–90`: BERT and XLM-R create a
zero token-type tensor on each forward; DistilBERT uses its inverted model mask;
Jina receives IDs without a mask; ModernBERT and Nomic use their own Candle
adapters. The model and tokenizer are retained fields, not cloned for an encode
(`src/encoding/dense.rs:115–128`). Candle's internal kernels and storage locks
were not read; this map stops at the served adapter boundary.

### Allocations, copies and CPU/device movement

This inventory names explicit Tessera allocations on the routes above. It is
not an allocator trace: tokenizers, Candle, ndarray operators, Rayon and the
shared worker codec can allocate internally. Their exact allocation counts and
bytes require the next measurement box.

| Stage | Explicit per-call work and source |
| --- | --- |
| Outcome preflight | `encode_outcome_batch_with` allocates refusal, accepted-reference, original-position and embedding collections (`src/api/embedder/dense.rs:568–590`), then collects ordered outcomes (`639–656`). It scans all inputs, chunks, vectors and refusals, never prior request history. |
| Role tokenization | Each `encode_with_prompt` validates the prompt, allocates `[prompt,text].concat()`, invokes the tokenizer, scans whitespace/offsets, and copies IDs and masks to two vectors (`src/core/tokenizer.rs:214–250`). Prompt validation itself tokenizes prefixes (`180–204`). Thus **two source passes per accepted outcome** understates total tokenizer invocations: configuration and prefix checks also run. `encode_batch_with_prompt` is an iterator, not a parallel tokenizer API (`253–273`). |
| Legacy tokenization/padding | `encode_unchecked` copies IDs and masks (`src/core/tokenizer.rs:276–296`). Batch tokenization allocates the collection (`597–605`); padding creates temporary pad vectors and can grow each ID/mask vector (`549–558`). Batch model input then copies IDs into an i64 vector and builds model and per-item pooling masks (`src/encoding/dense/inference.rs:506–550`). |
| Single-input tensors | IDs are converted into an i64 vector and tensor (`src/encoding/dense/inference.rs:63–68`); another i64 vector/tensor holds the model mask (`381–397`). The pooling mask is a third conversion (`452–456`). On an accelerator, these input tensors cross the host/device boundary; exact physical copy behavior belongs to Candle and is unchecked here. |
| Model output | The **whole** `[L,H]` output is cast to F32, moved to CPU, flattened and copied into a `Vec<f32>` (`src/encoding/dense/inference.rs:405–422`). Tensor batches cast/move the whole `[B,L,H]` once, then copy each sample (`565–587`). Device-to-CPU completion is in the timed path; exact synchronization operations are unchecked. |
| Pooling | `apply_pooling` clones the whole flattened array into an owned matrix (`src/encoding/dense/inference.rs:99–102`), even when CLS then copies only row zero (`src/utils/pooling.rs:49–50`). Mean pooling starts a zero vector, adds each valid row, then divides (`84–99`); allocation behavior of those ndarray expressions is unchecked. Max keeps one result vector (`133–153`). |
| Final vector | Matryoshka slicing copies when requested; normalization produces another vector (`src/encoding/dense/inference.rs:132–152`, `src/utils/normalization.rs:75–81`). Finite-value scans occur in the encoder's counted wrapper and its constructor (`inference.rs:259–272`, `src/core/embeddings.rs:451–465`), and dimensions are checked by the facade (`src/api/embedder/dense.rs:618–629`). Legacy `DenseEmbedding::new` checks finiteness and retains the source string (`src/core/embeddings.rs:247–275`). |
| Window planning | Joined string, content offsets, special prefix/suffix, plans and spans are allocated (`src/core/tokenizer.rs:360–455`). The special envelope uses two small encodes and copies prefix/suffix (`459–476`). Every window copies overlapping IDs and allocates an all-one mask (`src/runtime/window.rs:142–165`). The facade collects window references and output vectors, then rebuilds per-input result collections (`src/api/embedder/dense.rs:745–798`). |

For bge-base's `H=768`, F32 materialization is `4*L*768` bytes per item:
98,304 bytes at 32 tokens, 1,572,864 at 512. CLS needs 3,072 result bytes.
Selecting CLS on device before transfer would reduce these materialized output
bytes by 32× or 512×, and eliminate the second whole-matrix clone. These are
byte ratios, **not end-to-end speedups**. Model dimensions and CLS/normalization
are declared at `models.json:838–853`; present transfers and copies are above.

### Permits, locks, resource accounting and handoffs

* The process-wide inference gate is exclusive across callers and models
  (`src/runtime/inference.rs:14,96–100,170–217`). It defaults to 16 queued callers
  and a 30-second admission deadline (`11–12`). It holds a bookkeeping mutex
  only while queueing/admitting; it releases that mutex before returning the
  permit (`177–194`). Contention waits on a condvar; drop briefly locks state,
  clears occupancy and wakes all waiters (`103–110,237–247`). Timeout removal
  scans the **bounded waiter queue**, not input history (`277–280`).
* Single and outcome/window group permits cover CPU materialization, pooling
  and normalization (`src/encoding/dense/inference.rs:425–459,24–59,205–236`).
  Tensor batching releases its permit after the batch CPU transfer, **before**
  per-item CPU pooling (`565–595`). These are different contention boundaries.
* A chunk containing many items can monopolize one permit while its Rayon tasks
  finish. Raising the wait-queue bound does not increase compute concurrency.
  Different processes have separate gates. No claim is made about downstream
  Metal command-queue serialization.
* CPU preflight requests a two-thread ceiling (`src/runtime/model.rs:82–84`).
  Calling `configure_cpu_threads` before constructing the model can select a
  higher ceiling; first configuration wins. Both Rayon and Candle settings are
  bounded; Accelerate's own thread setting is forced to one on macOS
  (`src/runtime/threading.rs:57–84,87–117`). No new pool is explicitly constructed
  by each encode. Rayon handoffs occur on outcome batches and window groups.
* The builder defaults to no requested size or yield; it resolves a conservative
  batch size at build time (`src/api/builder/dense.rs:46–55,297–307`). The default
  policy has sequence 512, item ceiling 16, token ceiling 2,048 and attention-cell
  ceiling 1,048,576 (`src/runtime/policy.rs:11–16,387–388`): full-size sequences
  imply a conservative batch of four (`233–253`). An item ceiling of 16 therefore
  does **not** mean the default model runs 16 full windows together.
* Both outcome and tensor paths can sleep between chunks if the caller explicitly
  sets `yield_ms` (`src/api/embedder/dense.rs:379–384,596–599`). Default is absent;
  the worker does not set it (`crates/tessera-worker/src/engine.rs:57–63`). A
  performance experiment must record it instead of attributing caller-requested
  yielding to model speed.
* Batch admission uses `B*max(L)` and `B*max(L)^2`, even for the unpadded outcome
  path (`src/core/tokenizer.rs:267–272`, `src/runtime/policy.rs:349–381`). Activation
  admission likewise uses all items at the longest sequence before their parallel
  forwards (`src/encoding/dense/inference.rs:213–225`). This is conservative
  admission arithmetic, not evidence that these forwards contain padding.
  The scratch estimate includes hidden, attention and feed-forward buffers with
  1.5× headroom (`src/runtime/estimate.rs:50–86`). Removing that headroom without
  measured memory evidence is not a speed fix.
* Job accounting is stack-local counters, no mutex (`src/runtime/job.rs:17–41`).
  Residency reserves under a separate short-lived mutex at load and releases at
  drop (`src/runtime/residency.rs:59–98,105–130`); it is not acquired per encode.
  No whole model/state clone, disk write/sync, model load or network fetch appears
  in the inspected warm dense encode paths. They loop over the current inputs,
  tokens, windows and dimensions. Backend-internal work is unchecked.

### Worker and first-vector path

`main` prepares process resources before locking stdin/stdout for the session
(`crates/tessera-worker/src/main.rs:20–31`). Those stream locks span the session;
the session accepts Start, configures threads, loads the model and emits Ready
(`crates/tessera-worker/src/session.rs:26–46`). Ready does not warm a model
forward: the empty outcome call checks configuration only
(`crates/tessera-worker/src/engine.rs:65–67`).

For every Embed: shared frame read/check → `Engine::encode` → ordered output
validation → shared frame write (`session.rs:47–70`, `engine.rs:116–205`).
Tessera allocates a text-reference vector, outcome vector and wire-item vector;
clones each output ID; and calls `encode_vector` on each F32 slice (`engine.rs:121–158`).
The wire codec's expansion, temporary buffers, writes/flushes and locks are
**unchecked**: their implementations belong to the pinned shared crates, outside
S0. The pin is `1605372c1cd176cf9b1d54f3290e1a94a03c39cd`
(`crates/tessera-worker/Cargo.lock:971–982`). Budgeted raw vector payload is
`B*D*4`; shared frame validation applies separately (`crates/tessera-worker/src/policy.rs:44–66`,
`crates/tessera-worker/README.md:26–30`). Wire payload must be measured as encoded
bytes, not assumed to equal raw F32 bytes. A shared-code change needs Apollo's
agreement and another repository handover.

Any overlength item makes the whole Embed fail after outcomes are obtained;
some accepted neighbours can already have been forwarded. No Vectors frame is
sent (`engine.rs:126–138`). This distinction matters to refused-request cost
and must remain separate from successful throughput. Normalizer-erased content
also fails the whole worker request (`163–171`). The existing protocol tests
assert Failed/exit-one/no later vectors (`tests/protocol/never_cut.rs:7–29,87–115`).

At construction, the dense loader reserves residency, resolves artifacts, loads
the tokenizer/config, estimates activation space, maps weights with the chosen
dtype/device and constructs the adapter (`src/encoding/dense/loading.rs:42–49,66–100,123–154`).
Installed loading validates **every declared artifact** by size and streamed
SHA-256 before returning (`src/models/loader/installed.rs:214–254,367–410`).
Worker `registry_id` reads the manifest first (`engine.rs:30–32`,
`installed.rs:190–195`), then the constructor reads it for integrity checking.
For the declared bge-base set, verification reads 438,667,685 artifact bytes
(`certification/specs/bge-base-en-v1.5.json:9–24`), followed by model loading/page
access. Physical disk I/O depends on the page cache and is unmeasured.
The installed route has no fetch; the online resolver can fetch absent files at
construction (`src/models/loader.rs:41–63,95–120`). No integrity bypass is proposed.

### Metal: claims and current boundary

`docs/METAL.md:17–20` records historical compile/model-free checks. It explicitly
does not certify accelerator dtype or CPU parity (`68–79,107–113`). The checked
bge-base profiles declare CPU/F32 (`certification/specs/bge-base-en-v1.5.json:26–34`
and its other profile capability entries). A device-creation or dtype-admission
test is not a real-model numerical certificate. S0 has not inventoried all
historical accelerator evidence and makes no broader absence claim.

Two statements in that document have drifted: current `scripts/check:15–19`
does include a macOS Metal leg; and guarded `metal_device_at` now exists
(`src/backends/candle/device.rs:19–25`), while `docs/METAL.md:50–53,112` says
nonzero ordinals have no guarded route. Direct `Device::new_metal` remains a
separate unguarded API. Auto-selection still discards accelerator errors and
can return CPU (`device.rs:54–71`). A benchmark must use an explicit device and
record the actual location, so a fallback cannot masquerade as Metal.

F16/BF16 pass Tessera's accelerator gate; CPU requires F32
(`src/runtime/load.rs:27–43`). Acceptance and two-byte parameter accounting do
not establish kernel support, speed or answer accuracy. The worker currently
selects CPU/F32 explicitly (`crates/tessera-worker/src/engine.rs:57–63`), so a
library Metal experiment alone does not accelerate Apollo's worker service.
The old script also invokes plain `cargo test` and formatter `--check`
(`scripts/check:8,18,21–24`); follow-on boxes must name the mandated actual
formatter and nextest commands, rather than execute that script unchanged.

### Cost model and length mix

For a chunk with real complete lengths `L_i`, `R=sum(L_i)` and `M=max(L_i)`, tensor
batching processes `P=B*M` token rows. Approximate dense transformer work has
a linear component in P (projections/feed-forward) and an attention component
in `B*M²`; unpadded single-item forwards instead use R and `sum(L_i²)`, plus
one forward's setup per item. Neither formula alone models kernel utilization
or memory bandwidth. Admission quantities are separately the conservative
values identified above.

For each 20 inputs of the proposed J1 mix at batch four, unsorted tensor batching
has `R=2944`, `P=8704`, actual squared lengths `1,126,400` and padded squared
lengths `4,259,840`. Length buckets across this exact 10,000-item job eliminate
padding: counts 6,000/2,000/2,000 are all divisible by four. The linear-work ratio
is 2.96 and attention-work ratio 3.78. Those are arithmetic ceilings on the
corresponding work reductions, not a prediction of 3.78× throughput. The current
worker has **P=R physically** and 10,000 forwards; length sorting alone removes
no model padding there. It may affect scheduling and conservative admission.

For J3, capacity is `512-2=510`, stride `510-64=446`, and window count is
`1+ceil((4096-510)/446)=10`. Nine overlaps repeat 576 content tokens; twenty
special tokens bring 4,096 content tokens to 4,692 forwarded tokens. Formula
and ownership are at `src/core/tokenizer.rs:395–403` and
`src/runtime/window.rs:77–127`. Maintaining this count is a correctness
constraint; making it smaller by losing coverage is not an optimization.

Ranking is a view based on local source cost and risk, not a benchmark verdict.
Every gain below is an **unmeasured hypothesis**; zero gain or a slowdown remains
possible. If fraction f of measured wall time belongs to the changed stage and
that stage improves by factor k, overall speedup is `1/((1-f)+f/k)`. Use measured
phase fractions to replace the ranges; do not multiply speculative gains together.
